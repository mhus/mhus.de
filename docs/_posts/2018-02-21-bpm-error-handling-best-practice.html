At first we tried to catch all errors and handled them with an End/Terminate entity. Looking back it was an odd way to process the exception states.

The focus should be on maintenance and most of all on the customers using the system. Customers don't want to reinitialize a process every time an error occurred. They want the maintainer to fix it and let the process flow. Maintainers don't want to have much work with processes running.
I want to show two very common scenarios that happen in real life:
  1. All processes are based on tasks using operations working over the network. Maybe sending mails using a database etc. A lost network connection (maybe only a segment) will cause a lot of tasks to fail and trigger the error handling.
  2. A user creates a process instance and inserts data that's simply wrong. But the data can only be validated later in the flow. For example a wrong customer or contract id.
The first case shows a technical problem. It should be fixed by the administrators and then the processes should be restarted and do the work. It's a technical failure.

The second case shows a professional problem. We have the wrong information from the user. A task will fail and can't be done, even if it is retried. In this case a task error handler trail must be followed. And important: Different incidents could occur.

To implement this concept we changed the definition of automatic tasks with connectors. A connector should throw an exception if something technical went wrong. This exception should force the task to change its status to 'failed'. In this case we can retry the task if the technical problem is solved.

Next we check the return values of the connector. If something professional went wrong the returned data should contain such information, like "returncode=-5" or empty values "customerId=". Small post processor scripts can check the data and fire error handlers to jump into another part of the process.

The 'checkStatusError' script will change the status of the task to 'failed'. It's the situation of a technical failure.

In this way processes are more robust, customers are happier and the visual representation is clearer. It's a win-win situation ;-)
